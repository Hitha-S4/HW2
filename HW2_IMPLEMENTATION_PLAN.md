## 2. Essential paper concepts

### 2.1 Mutation testing

A mutant is an artificial faulty version of a program created by applying a small syntactic change, such as changing an operator or deleting a statement. A test detects/kills a mutant when it reaches the changed code and its observed result differs from the original test result, normally through a failed assertion or an exception.

The mutation score is the fraction of considered mutants killed by a test suite:

```text
mutation score = detected mutants / considered mutants
```

The score is used as a proxy for test-suite effectiveness because real faults are generally unknown in advance. A higher score is commonly interpreted as evidence that a suite is more likely to detect real faults, although it is not a guarantee.

For this homework, the important artifact is not only the final score. Major must preserve the detailed relationship between tests and mutants: which tests kill which mutants, along with the mutant log and summary.

### 2.2 The coupling effect

The coupling effect is the hypothesis that a test suite capable of detecting a sufficiently representative set of simple faults (mutants) will also detect more complex faults, including real faults. Mutation analysis depends on this assumption: if real faults are not coupled to the generated mutants, a suite can have a high mutation score while still missing that class of real fault.

The paper found that the coupling effect held for many, but not all, real faults. Its result is therefore evidence that mutation score is useful, not evidence that mutation score completely represents all real-world defects.

### 2.3 The paper's research questions

The paper asks:

1. **Are real faults coupled to mutants generated by common mutation operators?**
2. **What kinds of real faults are not coupled to those mutants?**
3. **Is mutant detection correlated with real-fault detection?**

Homework 2 uses the paper's setup and artifact-generation method, but does not ask you to answer those research questions statistically. Homework 3 will use the generated artifacts for analysis.

### 2.4 The paper's high-level methodology

The paper:

1. Located real bug-fixing revisions.
2. Isolated a faulty version and fixed version differing only by the bug fix.
3. Obtained developer-written test suites.
4. Generated additional test suites automatically on the fixed version.
5. Generated mutants and ran mutation analysis.
6. Compared real-fault detection and mutant detection.

Defects4J already supplies minimized, reproducible bugs with buggy/fixed revisions and bug-fix metadata. Therefore, this homework starts at the practical equivalent of steps 2, 4, and 5. You do not need to mine version-control history yourself.

## 3. Paper details that directly affect this homework

### 3.1 Fixed versus buggy versions

The paper labels:

- `V1`: the faulty version.
- `V2`: the fixed version.

For this homework:

- EvoSuite generation must use the fixed version, `<BugID>f`.
- Major mutation analysis must also use the fixed version, `<BugID>f`.
- The fixed version is the baseline that every retained generated test must pass.

Do not accidentally generate regression tests against `<BugID>b` or run Major on the buggy version. That would produce artifacts inconsistent with the rubric.

### 3.2 Restricting the target classes

The paper generated mutants only in classes modified by the bug fix. This avoids allowing unrelated code to dominate the mutation score and keeps the experiment focused on the real defect.

Homework 2 explicitly requires the same restriction for both tools:

- EvoSuite targets the bug-fix-modified classes.
- Major mutates the bug-fix-modified classes.

Defects4J's scripts default to the modified class list when no broader class option is supplied. Verify that behavior in the logs and metadata rather than assuming it silently worked.

Useful command:

```bash
defects4j info -p <Project> -b <BugID>
```

Record the modified classes reported for every selected defect. These class names should agree with the class list used by the generation and mutation commands.

### 3.3 Generated test-suite repair

The paper's repair workflow is:

1. Remove test classes/methods that do not compile.
2. Remove tests that fail on the fixed version.
3. Repeatedly remove non-deterministic tests.
4. Stop only when the suite passes five times in a row.

Defects4J provides `fix_test_suite.pl` for this process. The script documentation says it removes uncompilable tests and failing tests, then requires five consecutive passing runs. Use that supported workflow rather than deleting arbitrary files manually.

Important distinction:

- A generation run is one EvoSuite invocation.
- The resulting suite may be repaired by removing invalid tests.
- The final suite submitted must be the repaired Java source, not merely the original archive.
- If repair removes everything, that run does not provide a useful submitted suite; record it and generate a replacement so that the final defect has 20 usable suites.

### 3.4 Major's mutation operators

The paper describes four operator groups:

| Paper description | Major operators in this Defects4J setup |
|---|---|
| Replace constants | `LVR` |
| Replace operators | `AOR`, `LOR`, `SOR`, `ORU`, `ROR` |
| Modify branch conditions | `COR`, `ROR` |
| Delete statements | `STD` |

The Defects4J `run_mutation.pl` documentation lists the default set as:

```text
AOR LOR SOR COR ROR ORU LVR STD
```

Use the default set unless the instructor gives a different instruction. Record the exact operator set in the README. Do not silently omit an operator or add a different tool's operator.

`ROR` appears in both the operator-replacement and branch-condition descriptions because it is relevant to relational-condition mutations. It should be run once as part of the Major default set, not duplicated manually.

### 3.5 Equivalent mutants

The paper did not remove equivalent mutants. An equivalent mutant behaves the same as the original for all tests, so it cannot be killed even though it may be counted in the denominator. This can make absolute mutation scores look lower.

For Homework 2, do not manually edit away mutants merely because they appear equivalent. Submit Major's actual output. Homework 3 can account for the results using the recorded artifacts.

### 3.6 Why coverage matters, even though Homework 2 does not calculate it

The paper warns that mutation score and real-fault detection can both increase simply because a suite executes more code. It therefore compares results both with and without coverage control, using only mutants in code covered by both suites for the controlled comparison.

Homework 2 does not require coverage output. Nevertheless:

- Keep the target-class restriction exact.
- Keep all 20 runs separate.
- Preserve the kill matrix and summary.
- Do not compare or aggregate suites during artifact generation.

Those choices preserve the information needed for Homework 3's analysis.

## 5. Fault categories for the README

The paper's Section 3.2 groups uncoupled real faults into three broad explanations:

### A. Mutation operator needs strengthening

Examples:

- Statement deletion that cannot delete control-flow statements.
- Swapping same-typed arguments.
- Omitting an argument in an overloaded call.
- Replacing a library call with a similar library call.

### B. A new mutation operator is needed

Examples:

- Omitting a chained method call.
- Replacing a getter/setter with direct field access.

### C. No suitable mutation operator exists / inherent limitation

Examples:

- Algorithmic changes.
- Code deletion where the tested behavior is already covered by another path.
- Violated preconditions, postconditions, or invariants.
- Numerical overflow/underflow/NaN behavior.
- A specific literal replacement not represented by Major's default replacement.

For each selected Defects4J bug, classify the actual bug fix based on the code change, not based on whether Major happens to generate a mutant for it. Keep the classification concise and explain why it is reasonable.

## 8. Run Major once for every suite

The Defects4J mutation wrapper is:

```text
run_mutation.pl -p project -d suite_dir -o output_dir
                     [-v version] [-f include_pattern]
                     [-m mutation_operators_file]
```

Its documented defaults are:

```text
AOR LOR SOR COR ROR ORU LVR STD
```

It also defaults to mutating only classes modified by the bug fix. Do not use `-A`, because that broadens mutation to all relevant classes. Do not use a broader loaded-class list.

The conceptual command is:

```bash
"$D4J/framework/bin/run_mutation.pl" \
  -p <Project> \
  -d "$WORK/mutation_input" \
  -v <BugID>f \
  -o "$WORK/mutation_output"
```

The input archives must be named in the format expected by Defects4J, for example:

```text
<Project>-<BugID>f-evosuite.1.tar.bz2
<Project>-<BugID>f-evosuite.2.tar.bz2
...
```

If the final repaired source is arranged in a custom directory tree for submission, keep a separate mutation-input directory in the Defects4J archive format. The submission tree and tool-input tree do not need to be identical.

### Preserve outputs immediately

Major/Defects4J writes mutation results to its output working directory and later runs can overwrite them. After each suite:

1. Identify the mutant log.
2. Identify the kill matrix.
3. Identify the summary.
4. Copy them immediately to:

```text
<Project>-<BugID>/mutation/suiteNN/
```

Use stable, descriptive names if the tool's names are ambiguous, for example:

```text
mutant.log
kill-matrix.csv
summary.txt
```

Also preserve the original tool log if it helps reproduce the run. Do not fabricate a matrix or copy the same output into all 20 directories.

The required mutation organization is:

```text
<Project>-<BugID>/
└── mutation/
    ├── suite01/
    │   ├── mutant log
    │   ├── kill matrix
    │   └── summary
    ├── suite02/
    │   ├── mutant log
    │   ├── kill matrix
    │   └── summary
    ...
    └── suite20/
        ├── mutant log
        ├── kill matrix
        └── summary
```

### What to verify for each mutation run

For every suite, verify:

- It is the correct project and fixed bug version.
- Its test source is the corresponding suite, not another suite.
- The modified-class restriction is active.
- The operator set is exactly the recorded set.
- The mutant log is non-empty or the tool clearly explains a zero-mutant result.
- The kill matrix identifies the suite's individual tests and mutant outcomes.
- The summary is from this run.

1. **Using a paper project.** Chart, Closure, Math, Time, and Lang are forbidden for the selected project.
2. **Using the buggy version.** Both generation and mutation analysis must use `<BugID>f`.
3. **Mutating all classes.** Do not use the option that broadens Major beyond bug-fix-modified classes.
4. **Counting raw runs instead of usable suites.** A suite that cannot compile or pass five fixed-version repetitions is not a final suite.
5. **Reusing seeds.** Every suite for a defect must have a distinct seed.
6. **Running only one mutation analysis.** Every one of the 20 suites needs its own Major output.
7. **Letting outputs overwrite.** Copy the mutant log, kill matrix, and summary immediately after each run.
8. **Submitting archives instead of source files.** The test-suite deliverable requires `.java` source files in the stated suite directories.
9. **Including the project checkout.** The ZIP must contain artifacts, not compiled projects or build directories.
10. **Writing unsupported bug descriptions.** Read the actual Defects4J fix and tests for each chosen defect.
11. **Treating mutation score as proof.** The paper supports a correlation, not a guarantee that every real fault is represented.
12. **Doing Homework 3 early.** Do not add coverage or statistical analysis to Homework 2 unless the instructor separately requests it.
